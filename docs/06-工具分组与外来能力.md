# 工具分组、外来工具、MCP 与权限持久化 —— 设计稿

> 状态：待确认后实施
> 前置结论：外来工具**允许执行本体代码**，来源安全由供应链（用户）保证。

## 一、现状缺口

| 能力 | 现状 | 缺口 |
|---|---|---|
| 分组 | 路径中间段可任意，`build_tree` 已支持自动合成中间节点 | 清单无 `groups` 概念，CLI 无法创建分组、无法指定挂载点 |
| 外来工具 | `load_manifest` 强制白名单 `BUILTIN_TOOL_PATHS` | 完全无法加载清单外工具 |
| MCP | `/mcp/fs/*` 是本地函数假扮 | 无 JSON-RPC 协议实现 |
| 权限 | 判定逻辑健全（9/9 通过），但恒为空表 | 无持久化、无 CLI |

## 二、分组模型

### 2.1 语义

**分组 = 工具树上的中间节点**，不是独立存储对象。它由挂载在其中的工具路径**派生**得到。

```
/tool                        L1 资源根（固定）
/tool/os                     ← 分组（挂载点）
/tool/os/file/read           ← 叶子工具
/tool/mytools                ← 用户创建的分组
/tool/mytools/hello          ← 外来工具
/mcp                         L1 资源根（固定）
/mcp/filesystem              ← MCP 服务器 = 一个分组
/mcp/filesystem/read_file    ← MCP 服务器暴露的工具
/skill                       L1 资源根（固定）
/skill/fluid-particle-sim    ← skill 叶子（现为平铺）
/skill/mygroup/foo           ← 分组下的 skill
```

### 2.2 为什么分组不独立存储

若把分组作为独立条目写入 FlatStore，会产生两个真源：分组条目与工具路径的中间段可能矛盾（例如删除最后一个工具后分组该不该消失）。因此：

* **清单只记录挂载点**：每条工具/skill 记录自己的 `group`（可为空）。
* **分组的存在性由路径派生**：路径 `"/tool/mygrp/hello"` 里 `mygrp` 就是分组。
* **空分组的处理**：`groups` 表只记录「分组元信息」（描述），允许存在空分组以便提前建好挂载点；工具树中空分组仍会出现（由 `_synthesize_prefixes` 合成），描述取自 `groups` 表而非默认的「由子节点推断」。

### 2.3 数据结构

```python
@dataclass(frozen=True)
class GroupDef:
    """分组元信息。

    group_id 形如 "tool/os" / "mcp/filesystem" / "skill/mygrp"。
    """
    group_id: str          # 不含前导斜杠，形如 <root>/<name>
    description: str = ""
```

清单结构扩展：

```json
{
  "version": 2,
  "groups": [
    {"group_id": "tool/os", "description": "本机文件与命令"},
    {"group_id": "tool/mytools", "description": "用户外来工具"}
  ],
  "tools": [
    {
      "path": "/tool/os/file/read",
      "builtin": "os/file/read",          // builtin 与 source 二选一
      "group": "tool/os"                   // 可省略，默认取路径中间段
    },
    {
      "path": "/tool/mytools/hello",
      "source": {"kind": "python", "target": "./ext/hello.py", "callable": "run"},
      "description": "示例外来工具",
      "caps": ["read"],
      "schema": {"type": "object", "properties": {}, "required": []},
      "idempotent": true
    }
  ],
  "skills": [
    {"name": "foo", "group": "skill/mygrp", "description": "..."}
  ]
}
```

### 2.4 CLI

```bash
# 分组
harness groups list
harness groups create tool/mytools --description "我的工具"
harness groups remove tool/mytools            # 有成员时拒绝，除非 --force

# 内置工具（原有）
harness tools add /tool/os/file/read
harness tools add --preset files --group tool/fs2   # 装到指定分组

# 外来工具
harness tools add-ext --path /tool/mytools/hello \
    --target ./ext/hello.py --callable run \
    --description "示例" --caps read --idempotent

# skill
harness skills add ./SKILL.md --name foo --group skill/mygrp

# MCP
harness mcp add filesystem --command "npx -y @modelcontextprotocol/server-filesystem ." 
harness mcp list
harness mcp remove filesystem
harness mcp refresh filesystem      # 重新 tools/list 拉取工具清单
```

## 三、外来工具加载

### 3.1 安全立场

**允许执行本体代码，供应链负责。** 因此不再做白名单限制，但保留三项**非安全性**校验（防手误，不防恶意）：

1. 路径格式合法（B16/B19）；
2. `description` 单行（B9）；
3. 目标文件必须存在（加载时），否则该条目降级为「不可用」并记入 `problems`，不阻塞其他工具。

### 3.2 两种来源

```python
SourceSpec = {
    "kind": "python",          # 目前只支持 python
    "target": "./ext/hello.py" # 相对 workdir 的脚本路径，或 "pkg.module"
    "callable": "run"          # 脚本/模块中的函数名；缺省 "run"
}
```

加载逻辑（惰性，`resolve` 时才 import）：

```python
def load_ext_callable(spec, workdir) -> Callable:
    target = spec["target"]
    if target.endswith(".py"):
        # 按文件路径加载，要求文件在 workdir 内（防止手误写错绝对路径）
        mod = import_from_path(target, workdir)
    else:
        mod = importlib.import_module(target)
    return getattr(mod, spec.get("callable", "run"))
```

### 3.3 调用约定

外部工具函数签名统一为：

```python
def run(**kwargs) -> str:
    """返回字符串结果。kwargs 来自模型传入的参数（已按 schema 校验）。"""
```

若函数需要 workdir，可用 `def run(workdir: str, **kwargs)`，加载器按参数名注入（与 `build_tool` 的 hidden 注入一致）。

## 四、MCP（真协议）

### 4.1 传输

最小实现：**JSON-RPC 2.0 over stdio**（覆盖 90% 场景：`npx @modelcontextprotocol/server-*`）。
HTTP/SSE 传输留接口位，本期不实现。

### 4.2 生命周期

```
harness mcp add <name> --command "<cmd>" [--arg x]... [--env K=V]...
  ↓ 立即 spawn 子进程
  ↓ initialize        {"protocolVersion": "2024-11-05", "capabilities": {}, "clientInfo": {...}}
  ↓ notifications/initialized
  ↓ tools/list        → 每个工具转为 ToolDef，path = /mcp/<name>/<toolname>
  ↓ 持久化到清单（记录工具清单快照，避免每次启动都要拉起子进程）
  ↓ 关闭子进程（按需重启）
```

### 4.3 调用

`tools/call` 时惰性 spawn（或复用常驻进程），参数：

```json
{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"read_file","arguments":{"path":"/etc/hosts"}}}
```

结果 `content[].text` 拼接为字符串返回。

### 4.4 数据结构

```python
@dataclass(frozen=True)
class McpServerDef:
    name: str                  # 即分组名
    command: str
    args: tuple[str, ...] = ()
    env: tuple[tuple[str, str], ...] = ()
    tools: tuple[str, ...] = ()   # 上次 tools/list 的快照
```

清单里 `mcp_servers` 列表，工具条目仍按普通 `tools` 记录（带 `source.kind = "mcp"`），这样工具树逻辑不变。

## 五、权限持久化

### 5.1 文件

`<workdir>/.agent/permissions.json`

```json
{
  "version": 1,
  "agents": {
    "local": {"grants": {"/tool/os/shell/run": false}},
    "web":   {"grants": {"/tool/os/shell/run": false, "/tool/fluid": false}}
  }
}
```

**为什么按 agent 分**：`service.py` 用 `agent_id="local"`，`sessions.py` 用 `agent_id="web"`。同一份策略通常两边都要，但允许分别配置。

### 5.2 CLI

```bash
harness perms list [--agent local]
harness perms grant /tool/os/shell/run       # 恢复允许（删除例外）
harness perms deny  /tool/os/shell/run       # 拒绝
harness perms deny  /tool/fluid              # 拒绝整棵子树
harness perms show /tool/os/file/read        # 查看某路径的实际判定
```

### 5.3 接入点

* `service.py:_load_capability()`：`build_tree(store, load_permissions(workdir, "local"))`
* `sessions.py:95 / 695`：`build_tree(store, load_permissions(workdir, "web"))`

### 5.4 CLI 也要真实屏蔽

`harness service tree` 目前用 `agent_id="local"`，接入持久化权限后，被拒的路径不会出现在 CLI 输出里——与运行时一致。

## 六、索引简化（第三问）

### 6.1 实测数据

| 项 | 字符 | ~token |
|---|---|---|
| 叶子路径合计（17） | 325 | 217 |
| 叶子描述合计 | 428 | 285 |
| 当前 depth=2 索引 | 424 | 283 |
| 其中「由子节点推断」 | 133（31%） | 89 |

### 6.2 改动

1. **中间节点描述留空** → 索引只在有描述时输出 `路径 — 描述`，否则只输出 `路径`。省 133 字符（31%）。
2. **`depth` 语义修正**：`depth` 表示「展开到第几层」，`depth>=实际深度` 即全展开。当前 `depth=3` 与 `depth=2` 输出相同是 bug（`shown` 只收集了 L1+L2）。
3. **折叠阈值保留但调高**：`DEFAULT_L2_LIMIT = 40` 改为按总条目数判断，工具数 < 40 时全展开。17 个工具全展开仅 283 token，比两级折叠更省也更清楚。

## 七、实施顺序

| 阶段 | 内容 | 分支 | 验收 |
|---|---|---|---|
| A | 分组模型 + `groups` CLI | `feat-tool-groups` | 能建组、能挂载、空组可见 |
| B | 外来工具 | `feat-external-tools` | 加载 `hello.py` 并真实调用 |
| C | 权限持久化 + CLI | `feat-perm-persist` | deny 后 CLI 与运行时不显示/不可调 |
| D | MCP 协议 | `feat-mcp-protocol` | 真拉起一个 MCP server 并调用 |
| E | 索引简化 | `fix-tree-index-noise` | 索引体积降 30%+，语义正确 |

依赖：A 是 B/C/D 的基础（都要挂分组）。E 独立。

## 八、兼容性

* 清单 `version` 从 1 升到 2，`load_manifest` 对 v1 做**自动升级**（v1 无 `groups`，按路径推导补齐）。
* 现有 17 个工具路径不变，`builtin` 字段沿用原 `path` 白名单键。
