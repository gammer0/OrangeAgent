# C3 压缩接线修复记录

> 日期：2026-10-18　前置：`docs/06-上下文溢出修复记录.md`（C1 已修复）

## 1. 背景

上一轮修复了 C1 截断（单条工具结果 ≤ 4000 字符），实测生效。但任务仍会因上下文越界中断：

```
任务二：批量模式（失败，被截断）
0 秒   done   48 条   33142 tokens   101%
```

分析显示根因不是"工具结果太大"（C1 后最大仅 4000），而是：

> **上下文直接跳到 85% 以上，跳过 50% / 75% 两个压缩水位；
> 而 C3 压缩本来就因缺 `summarizer` 从未执行过。**

```
compress_available: False
ratio: 1.844  action: session_end
compressed: False  |  消息数仍为 41
watermark.compressed_at: set()     ← 两个水位一次都没触发
```

## 2. 方案

按"模型在工具结果返回后自动做一次摘要（无上下文单轮调用）"的思路实现 `summarizer`：

- 与主循环共用 `ReverseProxy`，但用独立 `session_id`（`<id>:summary`）隔离用量归集
- **不传 tools**，模型只能回文本，不会再次触发工具调用
- 输入先本地截断到 24000 字符，避免摘要调用本身超限

## 3. 修复过程中暴露的两个真实缺陷

### 缺陷一：`judge()` 与 `compress()` 争抢记账权（阻断性）

`watermark.judge()` 在判定后立刻 `mark_compressed(level)`，
而 `compressor.compress()` 开头又检查 `is_compressed(level)` 并抛 `ValueError`：

```
last_compress_error: I5: 水位 50 已触发过压缩，不得重复触发
```

于是 `compress()` 必然抛异常 → 被 `except ValueError` 静默吞掉 → **压缩永远不生效**。

**修复**：判定与执行解耦。`judge()` 只判定，`mark_compressed()` 由 `compress()`
在压缩真正成功后调用。

### 缺陷二：`compressed=True` 误报

`assemble()` 无条件返回 `compressed=True`，即使 `compress()`
因"记录不足以切分"原样返回。上层因此误以为压缩发生。

**修复**：用 `compressed_messages is not history` 判断是否真的重建过列表。

### 附带改进：压缩失败原因可见

新增 `ContextAssembler.last_compress_error`。此前失败完全静默，
这次的缺陷正是靠它才定位到。
