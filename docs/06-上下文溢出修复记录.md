# 上下文溢出修复记录

> 分支：`fix-context-overflow`　日期：2026-10-18
> 触发：agent 跑贪吃蛇任务时，会话 token 多次冲破 `capacity`（32768）。

---

## 1. 现象

| 会话 | tokens / capacity | 是否越界 | 工具结果字符占比 |
|---|---|---|---|
| `a9a24e3b7eea` | 37216 / 32768 | **114%** | 63.6% |
| `e4bd9a5670e5` | 35764 / 32768 | **109%** | 71.8% |
| `6d89e31532cc` | 14034 / 32768 | 43% | 60.5% |

工具结果确实是最大来源，但**占比高不是病根**——读源码本就该占大头。

## 2. 根因

### 根因一：C1 截断是死代码（P0）

`src/harness/truncate.py` 定义了 `truncate_result()`，默认上限 4000 字符，
实现与单测都完整。但全仓检索发现：

```
truncate_result  仅出现在 src/harness/truncate.py（定义处）
```

**从未被任何代码调用。** 设计文档 `04-初始配置清单.md` 标注 C1「默认开启（4000 字符）」，
实际完全不生效。证据：会话里出现 8021 字符的单条工具结果，是限值的两倍。

来源是 `/tool/os/file/read` 默认 `limit=400` 行，一次读整份 `main.py` 即吐 8k 字符。

### 根因二：C3 压缩静默跳过（P1）

`ContextAssembler.assemble()`：

```python
if action == "normal" or not self.enable_auto_compress or self.summarizer is None:
    return AssembleResult(..., compressed=False, action=action)
```

Web 服务构造 `ContextAssembler(capacity=...)` 时未注入 `summarizer`，
所以水位判定触发后直接无损退化。设计上「不报错」合理，但**没有任何地方暴露
「压缩不可用」**，运维面无法发现压缩从未发生。

### 根因三：MAX_STEPS 偏低（P1）

实测三轮任务（`a9a24e3b7eea`、`e4bd9a5670e5`）都在收尾前被 `max_steps=20` 截断，
收尾任务一次都没做完，导致需要额外开轮次补做，进一步推高上下文消耗。

## 3. 修复

### 3.1 C1 截断接线

`src/harness/executor.py` — 截断接在 `_content_of()` / `_failed_content()`，
它们是工具结果进入 `ToolMsg` 的唯一出口，一条改动同时覆盖成功与失败路径：

```python
def _content_of(value: Any, max_chars: int = DEFAULT_MAX_CHARS) -> str:
    if not isinstance(value, str):
        try:
            value = json.dumps(value, ensure_ascii=False, default=str)
        except (TypeError, ValueError):
            value = str(value)
    return truncate_result(value, max_chars=max_chars)
```

`max_chars` 沿 `execute_batch → _run_group → _run_one` 逐层透传，默认 4000。

失败路径同样截断——`traceback` 动辄上万字符，不截断会从另一个方向撑爆上下文。

### 3.2 压缩可用性可见

- `ContextAssembler.compress_available`：返回 `enable_auto_compress and summarizer is not None`
- `SessionManager.compress_available`：当前恒 `False`（未注入摘要器）
- `/api/health` 新增 `compress_available` 字段

这样「压缩从未发生」不再是静默行为。

### 3.3 默认值调整

| 参数 | 旧值 | 新值 | 理由 |
|---|---|---|---|
| `MAX_STEPS` / `loop.max_steps` | 20 | 40 | 多步工程任务常在收尾前耗尽步数 |
| `file_read` 默认 `limit` | 400 行 | 120 行 | 一次读整文件即吐 8k 字符；超长文件用 `offset` 续读 |
